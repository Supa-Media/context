# Obsidian parity — the phone layout, measured

The acceptance criterion for this work was not "tidier". It was **"it looks
exactly like Obsidian on iOS"**, asked for twice, so it is treated here as a
specification with numbers rather than as a direction of travel.

This folder is the evidence: the same components the app ships, rendered by
react-native-web at the reference's own size, photographed, and put beside the
measurements they were built to.

## The reference

Four screenshots of Obsidian on iOS, all 1320×2868 — **440×956 points at @3x**,
which is why every measurement below is in points at that width.

They are the owner's own vault and are **deliberately not committed**: they show
real folder names and real note content, and this repository is public and MIT
licensed (see `CLAUDE.md`, "This repository is public"). They live outside the
repo, at the paths cited in the pull request.

| | What it fixes |
| --- | --- |
| file explorer | the tree's rhythm, the vault footer, the drawer's height |
| reading view | paper, type, the floating chrome, the toolbar |
| editing view | the keyboard accessory bar and its dismiss key |
| long note, mid-scroll | the chrome floating *over* a continuous scroll surface, and the expanded Properties panel |

## Our side

Generated by `apps/mobile/scripts/design-shots.ts` and photographed with
Playwright at 440×956.

| File | State |
| --- | --- |
| `shots/explorer.png` | the file tree, drawer open |
| `shots/reading.png` | a note open |
| `shots/properties.png` | the same note with its Properties panel expanded |
| `shots/editing.png` | the note focused, with the keyboard accessory bar up |
| `shots/desktop.png` | the pointer layout at 1440×900 — a regression shot, not a parity one |

The editing shot has no soft keyboard in it, because a headless browser has
none. What it shows is the accessory bar and where it lands, which is the half
that is ours to get right — and that the bottom toolbar has put itself away,
which is what the reference does while the keyboard is up.

The `.html` files beside them are what Playwright opened. They are
self-contained: the markup, react-native-web's atomic stylesheet, CodeMirror's
base theme and the live-preview rules, all inlined. Open one in a browser at
440×956 and you are looking at the app.

Everything in them is the landing page's demo data (`placeholderData.ts`), which
is why they are safe to commit — there is no customer content in this folder by
construction.

## Reproducing

```sh
cd apps/mobile
pnpm exec jest --testMatch '**/scripts/design-shots.ts' --rootDir .
```

Then serve the folder and open each page at a 440×956 viewport. The harness is a
Jest file rather than a standalone script because Jest is where this repo's
TypeScript, JSX and react-native-web aliasing are already configured;
`jest.config.js` matches `__tests__/` only, so it never runs as part of
`pnpm test`.

## The measured spec, and what we got

Measured in the browser with `getBoundingClientRect` and `getComputedStyle`,
not by eye.

| | Target | Achieved |
| --- | --- | --- |
| Paper | `#FFFFFF` | `#FFFFFF` |
| Ink | `#222222` | `#222222` |
| Faint surface | `#FAFAFA` | `#FAFAFA` |
| Body type | 16pt / 24pt line | 16px / 24px |
| Body side margin | 25pt | 25pt |
| Explorer row pitch | 36pt | 36pt |
| Explorer indent step | 16pt | 16pt |
| Explorer left inset | 37pt | 37pt |
| Explorer row type | ~15pt | 15.5px |
| Touch target floor | 44pt everywhere | 44pt — 36pt rows carry 4pt `hitSlop` each edge |
| Top toolbar | transparent, content under it | transparent, absolutely positioned |
| Bottom bar width | 336pt (52pt clear each side) | 336pt at six actions |
| Bottom bar height | 66pt | 66pt |
| Bottom bar radius | half the height (~33pt) | `radii.pill` |
| Bottom bar gap below | ~25pt | `max(safe-area, 25)` |
| Chrome overlays content | yes | top bar and toolbar absolutely positioned; the scroller is full-bleed and pays for them in content padding |
| Properties, expanded | tinted rounded card, mark + muted key + ink value, `+ Add property` | same, at 15/22 |

## What is deliberately not matched

Recorded here rather than left to be rediscovered as bugs.

- **The top band carries a breadcrumb; Obsidian's carries nothing.** Obsidian
  names the note with an inline title inside the document, so its first screen
  of text scrolls up behind the floating chrome. Ours pins a breadcrumb there
  because it also carries folder navigation and the visibility chip, neither of
  which has another home on a phone. The note runs behind the *bottom* chrome as
  the reference does; the top band is occupied. Removing the breadcrumb in
  favour of an inline title is a product decision, not a styling one.
- **The bottom toolbar stays visible over an open file tree.** Obsidian's
  sidebar covers it. Ours floats above the drawer, which keeps the verbs
  reachable while the tree is open; the drawer pays for it with bottom padding
  so nothing is hidden underneath.
- **`+ Add property` is drawn and inert.** Adding one means *writing*
  frontmatter, and `frontmatter.ts` is a reader with no writer on purpose: a
  reader that misunderstands a line shows it oddly, a writer that misunderstands
  the same line rewrites somebody's note. Until there is a writer with a
  byte-for-byte round-trip test behind it, the row states where the capability
  will be, dimmed, and says so out loud to a screen reader.
- **Drag-to-dismiss is not wired, and cannot be here.** `keyboardDismissMode` is
  a `ScrollView` prop; the editable surface on a phone is a `TextInput` with no
  scroller around it. The accessory bar's dismiss key is therefore the only way
  out of the keyboard — which raises its importance rather than lowering it.
  `LiveEditor.tsx` carries the note for whoever moves this to a WebView, where
  `hideKeyboardAccessoryView` will also have to be flipped to `true` or a phone
  shows two stacked bars.
- **The desktop layout is not Obsidian's desktop.** It was not in scope and is
  not touched, beyond the palette and the marker rule which both surfaces share.
  `shots/desktop.png` exists to prove that.
