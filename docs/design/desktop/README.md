# The shell title band, and the bar it moved into

Evidence for two sections of `docs/decisions/desktop.md`. The first, "The
console reserves the space, the shell places the buttons", is the defect the
owner saw on the installed app: `createConsoleWindow`'s `titleBarStyle:
"hiddenInset"` keeps the traffic lights but removes the bar that used to hold
them clear of the page, and the hosted console drew its own chrome from `x: 0`
— so the close/minimise/zoom buttons sat on top of the active-context chip. The
fix was a band above every route, and it worked.

The second, **"The band moves into the bar"**, is what these pictures are of
now, and it is the owner's next sentence about the same corner: *"why is the
top forehead so big, this needs to be more compact and thin like notion"*. The
band was an empty `SHELL_TITLE_BAND_PX` strip sitting on a top bar exactly as
tall — 90pt of chrome before the first note, half of it drawing nothing. The
console's own bar holds the buttons now and pays `SHELL_TITLE_BAND_LEAD_PX` of
leading inset instead; the band stands down for it, and comes back the moment a
surface appears that cannot do the job.

Generated by `apps/mobile/scripts/shell-band-shots.ts` (the `.html`, checked in
beside this file) and `apps/mobile/scripts/capture-shell-band-shots.mjs` (the
`.png`, under `shots/`) — the same two-step technique
`docs/design/obsidian-parity` uses: real components, rendered by react-dom
exactly as react-native-web renders them for a browser, photographed by
Playwright. Every surface is shot in **both palettes**, because the complaint
is that two chrome rows in one colour read as a single slab, which is a
question about colour as much as about height.

**The traffic lights in these pictures are drawn by the harness.** The real
ones are native macOS chrome and nothing in this bundle puts a pixel there, so
a screenshot of a reservation would otherwise be a picture of an empty corner.
They are positioned from `SHELL_TRAFFIC_LIGHTS` — the same frozen object
`createConsoleWindow` passes to `trafficLightPosition` — so moving the constant
moves the stand-in and the real buttons together.

| | What it shows |
| --- | --- |
| `shots/console-mac-shell-{light,dark}.png` | **The change.** The console inside a Mac shell at a pointer density: no band, the buttons sitting in the top bar itself, and the `@seyi` chip starting after the 84pt lead. One row of chrome where there were two. |
| `shots/console-narrow-mac-shell-{light,dark}.png` | The same window dragged narrower than `narrowBreakpoint`. The compact bar is absolute and lies over the note, so it refuses the job and the band comes back — reachable by dragging an edge, not only by owning a phone. |
| `shots/sign-in-mac-shell-{light,dark}.png` | The sign-in screen inside a Mac shell. No frame, so no bar to hold anything: the band is unchanged here, which is why the handshake is a handshake and not a constant. |
| `shots/console-no-shell-{light,dark}.png` | The same console with no bridge on the page — an ordinary browser tab. No band and no leading inset: there are no buttons to clear, and 84pt of room for them would be 84pt of nothing. |

## The questions these pictures answer

**Did the forehead actually go?** `console-mac-shell-*.png` against
`console-narrow-mac-shell-*.png` is the before and after in one pair: the same
app, the same window, the buttons in the bar in one and in a strip of their own
in the other.

**Does anything that cannot hold them lose its band?** No —
`sign-in-mac-shell-*.png` and the narrow console both still draw it. That is
the property the whole design turns on, and the one a constant could not have
given: the band is not deleted, it stands down for exactly the surfaces that
took the job and returns for the ones that did not.

**Does an ordinary browser pay for any of this?** No —
`console-no-shell-*.png` is the same chrome it has always had.
